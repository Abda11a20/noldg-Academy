# F2 Authentication Report

## 1. Summary

Implemented the F2 authentication foundation on `feat/f2-auth`: target auth contracts and schemas, current-backend adapters, mock scenarios, capability flags, auth session state and guards, Arabic/English auth flows, shared OTP/chip/topbar UI, tests, and documentation. All local gates listed in section 4 passed. This was not exercised against a running live backend; live behavior is covered by adapter tests and contract evidence only.

## 2. Files created or changed

- `apps/portal/src/features/auth/`: auth schemas, form hooks, shared feature components, role/error/navigation helpers, and login, registration, verification, recovery, device, pending, suspended, and placeholder landing pages.
- `apps/portal/src/app/`, `apps/portal/src/shared/`, `apps/portal/e2e/`, and `apps/portal/scripts/`: real auth state/guards, lazy route and provider integration, Arabic/English strings, mock-driven browser tests, and E2E runner support.
- `packages/api/src/`: auth Zod contracts, endpoints, adapters for target and current API shapes, capability configuration, token/header handling, normalized errors, fixtures and MSW handlers; package export updates.
- `packages/ui/src/`: `OtpInput`, `Chip`, `Topbar`, public exports, and component tests.
- `packages/ui/vitest.config.ts`: keeps non-executable CSS and image assets outside the UI code coverage denominator; tests were expanded to cover optional Topbar and OTP edge branches, preserving the F1A 100% code coverage baseline.
- `docs/api-target-auth.md`, `docs/contract-differences.md`, `docs/decisions/ADR-009-auth-capabilities-and-adapters.md`, `README.md`, `CONTEXT.md`, and this report.
- `pnpm-workspace.yaml`, `apps/portal/package.json`, `pnpm-lock.yaml`: the two F2 form dependencies were declared and installed by the owner before implementation continued.
- `docs/reports/f2-*.png`: 18 screenshots generated by the Playwright flows. The four tracked F1A gallery screenshots were restored after the E2E run.
- `referencebackend/` was not edited, run, moved, or imported.

## 8. Deviations from the spec and why

- Audits were left to the owner as required; the supplied results are recorded in section 4.
- No live backend requests or live-browser flow were run. The backend folder is a read-only reference, and a running service/credentials were not provided. Live mapping is verified with adapter tests only.
- E2E covers the main auth journeys and error classes, but not every mock scenario as a separate page-level case. API and adapter tests cover many of the endpoint/error mappings; remaining page-level branches are a test gap.
- The spec asks for isolated unit tests for every hook and schema. Core schemas/helpers and cooldown behavior have direct unit tests, while remaining hooks are exercised through browser flows rather than all receiving dedicated unit tests.
- `gitleaks` was not installed in the environment; a manual credential-pattern scan was used instead.

## 9. Assumptions

- Mock mode implements the target contract as written in `docs/api-target-auth.md`; live mode capability defaults reflect the current backend evidence.
- Egyptian phone validation is not made stricter than the backend evidence because it only trims and caps values; target number policy needs confirmation.
- The current backend cannot provide email OTP, refresh-cookie, public catalog, student profile fields, or device change requests. UI reports unavailable capabilities gracefully.
- `https://api.example.test` was used only as a public build-time CSP origin placeholder for verification.

## 11. Risks and technical debt

- `VITE_AUTH_STORAGE=session` is a temporary fallback because the current backend has no refresh endpoint; target deployments should use the memory plus httpOnly refresh-cookie flow.
- Live catalog-dependent registration cannot proceed until authentication where the current API requires auth; the UI surfaces the capability limitation rather than crashing.
- Full audit has one moderate advisory per the owner’s output. The configured audit command fails at high severity, so it exited successfully; review the advisory details outside the sandbox.
- Install succeeded despite the Husky prepare script reporting `fatal: not in a git directory`; verify future installs occur in a Git checkout and monitor the deprecated ESLint warning.
- Dedicated unit tests for each hook and page-level E2E for every mock scenario remain incomplete.
